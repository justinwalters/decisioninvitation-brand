# Contributing to the identity

Start with `AGENTS.md`. Work from a brief and state the system version. The current release candidate is a design proposal; contribution is permitted, and approval is not implied.

## A useful change

Describe the communication problem, audience, artifact, and intended action before choosing a style. Identify which product statement supports the copy. A new channel should adapt a documented principle rather than introduce a competing identity.

Keep source changes reviewable. Edit vector masters, token sources, and templates, then rebuild derived files. A manually corrected export will be lost on regeneration. Give assets descriptive names; include variant and dimensions where useful. Keep temporary work outside the release download.

## Review requirements

| Change | Review evidence |
| --- | --- |
| Copy or channel adaptation | Relevant brief, actual destination, supported claim, accessible alternative |
| Mark or typography | Dated decision, source comparison, small-size and one-color proof, affected consumer list |
| Palette or semantic token | Dated decision, contrast results, light/dark examples, consumer impact |
| Application specimen | Fixture label, product-truth check, relevant screen and state |
| Release | File manifest, rebuild/validation result, representative visual proof, publication state |

Update `CHANGELOG.md` for a material change and the team's private adoption ledger for a consumer update. Start from `docs/adoption-register-template.md`; do not commit private receipts or automatically publish the completed ledger. Record exceptions with their exact asset, audience, reason, owner, and expiry. Exceptions are local; they do not silently amend the system.

## Release naming

Version as `major.minor.patch`. During `0.x`, a new creative direction increments the minor version; corrections and additional exports increment the patch. After approval, changes to recognizable identity, mark geometry, primary palette, or type roles increment the major version. Keep a dated decision with every recognizable change.

A preview may be shared to review the work. Label it “Identity proposal · 0.3.0” until the user approves a release. Hosting a preview does not certify product features or approve public marketing claims.
